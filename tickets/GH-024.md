# GH-24 — Recover retained workers after lifecycle configuration changes

Issue: https://github.com/MattGibney/Crew/issues/24

Retained workers previously rejected every plan difference as a combined plan/ownership failure. Disposal continued to use an older plan with no teardown; manually removed worktrees had no supported record-recovery path.

The manager can now review phase differences and blockers, then queue a human-approved recovery tied to task/run/environment and both plan hashes. The durable controller applies compatible lifecycle metadata without starting commands, replaying setup or changing the worker conversation. Prior plans and decisions survive crash/retry. Setup, Start, existing provenance, environment and permissions remain pinned; executable/new sources must match the retained base and canonical worktree. Dirty unrelated work stays intact, and disposal remains protected.

For an already absent and unregistered worktree, a distinct reviewed action retires the stale card, retains history and explicitly reports resource cleanup unverified. No cleanup, Git prune, force-stop, approval response or worker launch occurs. A Review recovery button starts only the manager discussion. Runtime/worker/hook uncertainty, foreign or symlinked identities and incompatible changes block with specific guidance.

Validation includes actual Git worktrees and lifecycle supervisors, teardown adoption, setup-once resume, dirty disposal refusal, source/ownership rejection, missing-path registration checks, manager MCP request/response, unrelated-worker isolation and controller restart after environment adoption but before task completion. Full-suite, UI and package results are recorded in the PR. Private evidence and screenshots stay outside Git.

This PR does not merge, release or change the installed application or user workspaces. Adding a missing stop command to a still-live runtime remains outside this recovery path.
