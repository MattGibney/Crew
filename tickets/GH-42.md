# GitHub #42 — Repeated assignments to retained workers

Ticket: https://github.com/MattGibney/Crew/issues/42

Completion records a finished assignment, not the end of a retained worker. The manager can queue a fresh explicitly human-authorized brief on that same worker, with a new assignment/run and the original native conversation, registered worktree, environment and behavior snapshot. Completed briefs/results remain immutable. Busy work continues until a verified safe boundary; queued work after reopening requires explicit manager start.

The manager tool is `assign_worker_followup`. Unexpected retained changes use read-only `review_worker_followup`, then explicit `approve_worker_followup_changes` with the exact fingerprint. These operations never authorize unrelated edits, widen effective sandbox policy, answer native approvals or bypass process/environment ownership. Failed recovery preserves files, context and queued direction. Explicit disposal ends availability and retains execution records.

Validation uses detached synthetic controller runs, manager MCP/store tests, compiled renderer browser acceptance, and opt-in actual subscription acceptance on disposable repositories. The native proof exercises research, authorized implementation and another refinement, recalling earlier context absent from the later briefs, with one thread/worktree and setup count one. Private evidence and screenshots remain outside Git.

Implementation is delivered as a PR to main. Merge, release and version changes require separate authorization. Worker archive UI is tracked separately in #43. TypeScript migration #37 must explicitly port the new assignment/adoption/evidence contracts when integrating this behavior change.
