# Existing project execution (AI-012)

Crew reads the selected commit’s Codex environment configuration and bounded applicable AGENTS, Claude and linked development instructions. Setup discovers commands without executing them. The project remains authoritative: Crew requires no repository changes or new lifecycle API.

Project analysis saves a generic local execution plan containing exact setup and named Start commands, source paths and hashes. Existing runtime choices are retained. The project form can select existing project setup or a worktree only. Missing or ambiguous instructions remain explicit; Crew does not invent cleanup or health checks.

Each worker receives a registered worktree with a compact, globally unique retained directory name. State stays in the configured private folder. If that folder contains spaces, new worktrees normally use a private persistent ~/.crew/worktrees instance namespace so established project scripts can retain their usual path conventions; existing recorded worktree locations remain unchanged. Before setup Crew verifies its canonical location, registration, pinned commit and source hashes. Setup runs once through the existing project command; interrupted or failed setup requires review rather than automatic replay. Start runs as an independently supervised foreground process. Resume retains the same session/worktree/data, reuses the existing Start action as needed and never silently reruns setup. Closing the window or restarting the controller adopts surviving owned processes.

An optional declared readiness command gates worker dispatch. Without one, Crew reports setup completion and foreground process liveness only; neither proves application health. Project instructions and actual task checks remain relevant. Exact scripts run in a shell rooted in the worker worktree, using a login zsh and Crew's launch defaults. Personal startup files remain active. These controller-owned host lifecycle commands run outside the Codex worker sandbox; Codex's shell environment policy applies to commands Codex launches, not these separate lifecycle processes.

## Managed Node and npm (GH-1)

Crew provides default Node/npm tools for project execution. It reads the selected commit's existing version declarations and applicable project instructions, then resolves compatible exact versions. Supported inputs are `package.json` (`engines.node`, `engines.npm`, `packageManager: npm@…`, and `volta.node`/`volta.npm`), `.nvmrc`, `.node-version`, `.tool-versions`, and explicit numeric Node/npm instructions in applicable `AGENTS.md`, `CLAUDE.md` and discovered `.claude` `SKILL.md` files. Numeric versions and bounded semver ranges are supported; aliases such as `lts/*` and other package managers require clarification.

Preflight inspects requirements without installing tools. The first authorized worker preparation installs missing versions in Crew's shared cache: `~/Library/Application Support/Crew/toolchains` on macOS and `~/.crew/toolchains` on Linux. All local project instances reuse that cache; worktree dependencies, builds and application configuration remain separate. Crew does not change the user's global PATH, shell profile or personal Node installation, and projects do not need a Crew-specific lifecycle API or source patch.

Setup, Start/resume, readiness, teardown and the worker process receive the same managed tool defaults. The launch PATH places selected managed tools before required system utilities, followed by inherited executable search paths. Crew preserves inherited environment variables and does not replace `ZDOTDIR`, disable startup files, or clear shell/Node/package-manager preferences. Explicit shell startup and Codex shell-environment settings may select different tools. Managed version validation verifies the installed defaults; verify actual command versions when configured overrides matter. Retained legacy controlled-shell paths are ignored without deleting their files.

Missing required Node declarations, conflicting declarations and unsupported version syntax stop default tool preparation with actionable guidance. Crew reuses a compatible cache entry or resolves a release within the declared constraints; when npm is unspecified, it uses that Node release's bundled npm version. It never guesses a personal version-manager path. Toolchain resolution does not prove Docker socket access, project service readiness or application credentials. Native Codex configuration continues to resolve user, trusted-project and managed settings; Crew does not copy local configuration or credentials into worktrees.

Downloads are verified before publishing a complete cache entry. Installation uses temporary locations and concurrent requests coordinate around the same version; an interrupted or failed installation must not become a usable cache entry. Permission, network and verification failures leave project work retained and identify the failed tool operation. The cache is shared storage, not a filesystem or container sandbox.

### Recovering an earlier failed setup

A tooling fix does not establish whether an earlier setup completed. Review the retained task's hook evidence and the project's existing setup/cleanup instructions first. An incomplete setup may already have created databases, containers or files even when the Codex worker never started. Ordinary resume must not replay that setup, reset data or remove the worktree.

The manager should explain the observed failure and propose a concrete recovery using the project's existing commands. Cleanup, reseeding or removal of partial resources requires explicit authorization scoped to those resources; shared resources and unrelated work remain untouched. If safe recovery cannot be established, keep the failed task and its evidence for review. A report from another Mac is evidence of the reported symptoms, not proof of the precise cause or current process/resource state on that Mac.

Stop terminates only owned foreground processes. Dependency services may remain running unless an explicit project stop command exists. Disposal requires the declared teardown when a runtime was started; absent or ambiguous teardown is a manager question, not permission for guessed cleanup. Dirty worktrees and uncertain ownership block removal. Results and task records remain. A successful declared teardown command does not independently prove every resource was removed; report any observed residual resources according to the project’s existing tooling.

Ordinary developer configuration is used as the project defines it, including inherited local settings and background behavior. Crew does not promise a provider-disabled mode, host firewall or hostile-worker security boundary. The generic flow uses established commands without requiring a project-specific source patch or lifecycle API.

Two-worker acceptance exercised actual local application health and seeded login, manager questions/answers, retained resume, controller/window recovery, targeted stop and declared teardown. Existing project-tool limits were retained: some assets required an additional project build and declared teardown omitted some project resources. Observed residuals were disclosed and preserved. This validates the measured integration, not all projects or production behavior. Private operational identities are excluded from the public record.

## Recovering retained workers after configuration changes (GitHub #24)

Lifecycle commands saved in Project Settings become available to existing workers on their next explicit retry/action (GitHub #45). Saving executes nothing, and an active command retains its snapshot. The worker keeps its original plan plus every replaced plan revision and attempt outcome. Updated commands use the retained worker’s verified baseline dependencies, prepared environment and permissions; configured and effective source bindings are recorded separately. A newer source hash does not claim the old worktree contains the newer file. Missing/changed worktree files, ownership, baseline and registration errors remain blockers.

A failed partial setup can be rerun through the explicit **Retry failed setup** action after correcting its command. The same worktree/context and prior failure remain, with single-use durable retry identity. Ordinary Resume never authorizes that replay. Successful setup remains setup-once. No separate plan-adoption step is needed merely to retry a corrected lifecycle command.

The older explicit recovery review below remains available for deliberate recovery decisions and missing-worktree retirement; it is not a prerequisite for applying ordinary command fixes.

Choose **Review recovery** in an inactive worker's details, or ask the manager to review that worker. This opens a discussion without starting work or changing resources. The manager's `review_worker_recovery` tool shows retained/current phase commands, timeouts and source evidence, exact blockers and a review hash. After the human approves the specific command and resource scope, `request_worker_recovery` queues the matching task/run/hash decision. Read task status to distinguish a queued request from its completed application.

**Reconcile lifecycle configuration** accepts reviewed resume, readiness, stop and teardown changes, including adding a missing teardown. Setup, Start, environment variables, permissions, existing provenance and other plan fields remain pinned. New provenance and all executable sources must match both the retained base commit and current canonical worktree. Unrelated retained documentation edits remain intact. Recovery requires the worker, lifecycle hooks and owned foreground runtime to have confirmed termination; it does not pause, kill, rerun setup or resume work. After adoption, resume or safe disposal is a separate explicit action. Failed provisioning permits teardown recovery without authorizing another setup attempt.

**Retire a missing worktree record** requires the owned path to be absent and no longer registered with Git, plus confirmed process/lifecycle evidence. It executes no cleanup or Git-prune command. The record becomes Retired in history and explicitly says resource cleanup is unverified. Task/run/history and recovery decisions remain. Existing or dangling links, foreign paths, remaining registration and uncertain shutdown block retirement. Normal disposal still refuses dirty work.

The environment recovery journal records the exact old plan, new hash, differences and decision before task completion. A controller restart can complete that same approved action idempotently. Changed decisions, stale runs or changed plan hashes require another review. A live project runtime lacking a graceful stop command remains blocked until a declared command is configured and explicitly requested; this flow cannot manufacture ownership evidence or infer how to clean shared services. A successful declared teardown remains command evidence, not independent proof that every external resource disappeared.
