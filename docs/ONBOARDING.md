# Crew setup

Crew guides the user through local tools, ChatGPT sign-in, the project, permissions and a summary. The manager and workers start only when explicitly requested; setup starts no microphone or business work. Existing ChatGPT authentication is used without API keys or credential-file reads.

## Project setup (AI-010)

Choose the local project folder and select **Set up this project**. Crew reads a bounded selection of code/documentation through the subscription-backed setup analysis, discovers actual Git branches and reads available Linear teams/projects through the configured Codex MCP connection. It validates and saves the resulting local settings and project-specific manager/worker instructions automatically. Previous settings and prompt files are retained by the save mechanism; cancellation or failed validation leaves saved settings unchanged.

The folder is canonicalized to its actual Git root and the repository name comes from that folder, rather than an invented AI label. An existing meaningful project name and stable repository ID are retained for the same folder. The starting branch is selected from actual Git refs, preferring the repository's recorded remote default; the user can choose another existing branch by name. No branch, path, team ID or project ID is invented. Project understanding omits draft/setup-review instructions; bounded source evidence is available in a collapsed section.

External tracking is optional. New project folders default to **No external tracker**. Enable Linear, GitHub or both and select a preferred tracker for new work. Linear lists real connected teams/projects; GitHub lists accessible repositories or verifies an explicitly entered owner/repository. Select the intended account mapping explicitly. Existing mappings remain saved and may be unverified; a discovered capability is not proof of issue/review/check access. Retry, switch or disable unavailable integrations while retaining valid local configuration. No tracker requires no external read or ticket before agreed local work. Existing task links remain unchanged when preference changes.

Branch and tracking choices save when selected. Advanced settings contain optional technical IDs, state paths and instruction-file locations; ordinary onboarding does not require raw JSON, Git ref syntax, Markdown editing or mandatory review checkboxes. A changed folder cannot silently inherit an unrelated project's team/project mapping. Existing task/chat identity and state directories remain protected, and active work/voice blocks applying settings.

## Worker application environments (AI-012)

Project setup reads existing committed Codex environment configuration and project instructions. Analysis can save the existing setup and Start action as a generic execution plan; **Worker application environment → Use existing project setup and Start action** also selects it. Missing readiness or teardown remains explicit. Saving runs no commands. Existing custom settings are retained, and changing project folders clears the old execution plan. See [Project execution](PROJECT-ENVIRONMENTS.md).

Crew resolves the project's required Node/npm versions from its committed configuration and explicit numeric instructions when preparing execution. Preflight inspects requirements without installing tools; the first authorized worker preparation installs missing compatible versions in Crew's shared cache (`~/Library/Application Support/Crew/toolchains` on macOS, `~/.crew/toolchains` on Linux). Instances reuse that cache. Crew supplies managed tools as launch defaults, retaining inherited discovery paths and shell environment without changing global tools or shell settings. Explicit Codex environment settings and personal startup files may override these defaults; verify actual command versions when overrides matter. Setup, Start/resume and worker execution begin with the same selected tool defaults. Missing required Node declarations, conflicting declarations, unsupported aliases and installation/network/permission failures remain actionable errors rather than a successful environment check. Saving project analysis alone installs no tools and launches no project commands. See [supported requirement sources](PROJECT-ENVIRONMENTS.md#managed-node-and-npm-gh-1).

An earlier failed setup stays retained after tools become available. It may have created partial application resources before failing. Review its evidence and authorize a specific project-defined recovery before cleanup or reseeding; resume does not silently replay incomplete setup. See [recovery guidance](PROJECT-ENVIRONMENTS.md#recovering-an-earlier-failed-setup).

## Permissions and recovery

Microphone permission is requested only by the user's explicit action, without a recording stream or voice call. Granted, denied, restricted, not-determined and unknown remain distinct. **Not now** defers voice. File checks probe the configured folders/branches/instruction files and a temporary write in Crew's state folder. These checks do not prove a worker's sandbox or a whole application environment is ready. There is no artificial LAN probe or blanket Local Network permission promise.

Missing config/Codex and malformed JSON do not prevent setup from opening. Runtime/sign-in checks use public supported app-server methods and sanitized results. Unknown or denied connections show a recovery action rather than a false success. Summary distinguishes local configuration, selected integration reads, microphone state and future ticket/environment validation.

New defaults use `~/Library/Application Support/Crew`; `--config` and `AI_MANAGER_CONFIG` stay supported. Stable bundle ID `local.voice.manager` remains for macOS identity continuity. See [storage migration](STORAGE.md). The app is local, one project per config/state/port. One installed app manages these isolated instances. Add project in the project switcher opens onboarding for a separate config/state/port/chat; the original project remains registered and its background work continues.
