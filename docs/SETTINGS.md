# Project instructions and manager controls

Tracked by [GitHub issue #3](https://github.com/MattGibney/crew/issues/3).

Open **Settings** in the Crew header. Global → General controls shared worker capacity on this Mac. Project → General renames the selected project; Sessions provides Start/Stop/Restart; Manager profile contains name, picture, personality, voice and manager instructions; Worker profile contains worker instructions. The floating navigation sits beside the content. Choose Update to edit, Save to persist, or Cancel to discard that editor’s unsaved changes. Save confirmations appear as dismissible toasts; guidance stays below the instruction editor. The instruction editors contain the complete replacement Crew-authored behavior for this project's manager and workers. A custom instruction save replaces that role's defaults. Optional manager name/personality fields are a separately visible, editable supplement; clearing them removes that supplement after Start/Restart. No hidden default personality is retained outside these settings. These editors do not expose or override Codex/provider system instructions, sandbox enforcement or tool schemas. Do not put credentials in instructions.

The default behavior includes communication, delegation, scope, reporting and the voice startup greeting. Crew adds separately identified runtime context: project/task/run identity, sandbox permissions, controller/report bindings, task briefs and relayed answers. Realtime receives the active manager behavior plus the selected voice and a factual connection event. Connection acknowledgement does not append another hidden greeting instruction or start a user turn.

**Save instructions** persists the current editor. **Cancel changes** discards only the unsaved draft. **Reset to default** loads the complete shipped default into that editor; save it to persist the reset. Resetting one role does not affect the other. Drafts survive switching between Settings and Conversation, and failed/stale saves preserve text. A concurrent saved change requires reviewing the latest version rather than overwriting it silently.

Manager saves remain pending until **Restart manager**. Saving never hot-applies a prompt or starts a turn. Settings shows a plain Start/Restart notice when saved instructions are not active; internal version checks remain in place without exposing hash labels. Restart resumes the saved native chat with the saved instructions; it retains conversation history, project tasks and workers. Stop followed by an explicit Start also applies saved instructions. Reloading the window or controller preserves the retained manager instructions and stopped intent; it does not silently activate a newer saved manager prompt.

Worker changes affect the next actual first launch. An already launched worker retains its original text and version on answers, pause/resume and controller recovery. Its retained task detail exposes that snapshot for review. Legacy workers recover their original prompt from the recorded run configuration; if that source is unavailable, resume refuses rather than changing behavior.

## Start, stop and recovery

- **Stop manager** immediately holds new conversation/voice requests, releases voice, waits for pending starts, requests native interruption and waits for terminal turn/approval evidence before confirming process exit. It does not stop the controller, workers, worktrees or environments.
- **Start manager** resumes the retained conversation and saved instructions. It never connects voice, activates a microphone, starts backlog or launches a worker. Use Connect voice explicitly for a new call.
- **Restart manager** uses the same safe stop, then resumes the same retained chat with saved instructions. Repeated matching actions share the transition; conflicting actions wait for its result.
- If native interruption, approval resolution or process exit cannot be confirmed, Settings shows an actionable error and holds new interactions. Pending approvals remain answerable in Conversation; review or decline them, then retry Stop/Restart. No approval is fabricated and no worker is killed to clear the error.

Workers report durable progress, questions and results while the manager is stopped. Their attention remains visible and can be discussed after Start. Stopping a single manager turn remains a separate **Stop current turn** control. Closing the window still releases voice while leaving the manager/controller and independent workers available in the background. Explicit application Quit remains separate.

## Persistence and integration

Settings are stored privately under this project's state directory at `prompt-settings/<projectId>.json`. Atomic replacement, file mode 0600, project identity, content hashes and optimistic version checks protect saved values. The configured Markdown files remain unchanged and provide the initial content when no settings save exists. Exact byte-for-byte untouched pre-settings shipped defaults are recognized by known hashes and upgraded to the complete visible defaults. Customized files, explicit saved settings and retained worker snapshots are never upgraded by this migration.

`manager-lifecycle.json` records project identity, held/running intent and the retained manager text/version. A transition persists held intent before changing the provider session. Only successful native activation advances the retained active version. A damaged or mismatched record fails closed and remains available for recovery. Do not delete state to clear a lifecycle error.

The instance-scoped HTTP contract is:

- `GET /api/settings`: project identity/name, manager identity/personality/voice profile, saved/default prompts, manager active/retained versions and pending changes, plus lifecycle state/error. `manager.savedBehaviorVersion` identifies the combined saved instructions and profile for lifecycle-event comparisons; `manager.saved.version` continues identifying only the unchanged instruction editor text.
- `PUT /api/settings/manager-profile`: `{voice?,name?,picture?,personality?,expectedVersion}`. Partial saves preserve omitted fields. Name/picture presentation updates immediately; name/personality activation waits for Start/Restart. Voice applies to its next call; existing calls are unchanged. Prior project-partition preferences migrate once when no explicit profile exists.
- `PUT /api/settings/prompts`: `{role,text,expectedVersion}`. Same-origin JSON only; invalid, oversized or stale edits leave saved settings unchanged.
- `POST /api/manager/lifecycle`: `{action:"start"|"stop"|"restart"}`. Same-origin JSON only. Update admission prevents new lifecycle work during an installation reservation.
- SSE `manager-lifecycle`: `{state:{state,error,activeVersion,retainedVersion}}` on the existing single event stream.

The separate multi-project change can route these endpoints to a selected project's own backend/config/state/port. This feature adds no registry or global prompt. The separate coordinated updater must use lifecycle transition/error evidence and installation admission; manager stop alone does not pause workers. Combined multi-project/updater integration requires testing after those independent PRs are integrated.

## Manager identity and personality (GitHub #35)

Choose **Update** beside Name and picture or Personality under Project → Manager profile. Leave the name blank for **Manager**, remove the picture for the Crew fallback, and leave personality blank to use only the existing instructions. Name/picture presentation changes on save, including historic message labels; it does not rewrite message text or change which native manager produced it. The identity remains an AI manager.

Personality is free text for tone, communication style and preferences. It is visibly configured alongside the existing full replacement instructions, with no separate personality model or engine. Both the name and personality join the retained instructions sent to native Codex for typed and voice conversations after explicit **Start/Restart** in Sessions. Saving, switching views and reloading do not activate new behavior or start a call/turn. A configured name takes precedence over the audio voice name when the manager introduces itself; the default greeting otherwise remains unchanged. Custom instructions remain byte-for-byte untouched. The selected audio voice is independent and is never changed by a name, picture or personality save.

Use a local PNG, JPEG or WebP up to 512 KiB and 2048 × 2048 pixels. The renderer checks decoding; the backend checks MIME/signature, encoded size, dimensions and canonical base64. Failed picture display falls back to the Crew mark. Pictures remain private in this project's `manager-profiles/<projectId>.json` and are not sent to Codex. SVG, arbitrary local paths and remote URLs are rejected. Names allow up to 80 characters and personality up to 8,000, excluding unsupported controls and secret-like material. Combined active instructions are limited to 64,000 characters; either editor rejects an oversized combination before saving.

Voice-only schema-1 profiles load with empty optional fields and their exact selected voice. The next save atomically writes schema 2 with private file permissions, project identity and optimistic version checking. Omitted patch fields are preserved. Invalid files are retained for recovery rather than reset. Saved presentation, the saved instruction editor and the retained combined native instruction snapshot are separate evidence; the pending notice covers changes to either behavior source. Pictures and voice selection do not create a restart notice.

Native activation also supplies the retained Crew snapshot as keyed `turn/start.additionalContext` with `kind: application` on actual typed turns, and `realtimeStartInstructions`/`realtimeEndInstructions` for native realtime handoffs. `thread/resume.developerInstructions` alone retained the initial developer history in a materialized chat on the tested installed Codex 0.163.0-alpha.10.2. The keyed context explicitly replaces prior Crew snapshots without editing native history, provider instructions, model/mode, user configuration or approvals. It contains only active Crew instructions and mechanical runtime context, never picture data or authentication. Ordinary saves cannot change that retained snapshot.

## Worker environment

Open Project settings → Worker environment to review and update lifecycle commands. Crew displays the existing supported format rather than converting executable arguments into shell text. Every command runs in that worker's own worktree. Direct command arguments have separate fields, including empty arguments and literal quotes/newlines. Timeout values are milliseconds (1,000–600,000).

Project execution plans expose Set up once, Start, Resume, Check readiness, Stop and Tear down. Direct hooks expose Set up, Start, Check readiness, Resume and Clean up. An absent command is explicitly shown as not configured. Source references and permission metadata describe the captured project configuration; edits in this page are Crew overrides saved in Crew's config, never edits to project or Codex environment files. A legacy PATH snapshot is visible as read-only compatibility metadata and is not applied at launch. Workers use managed tool defaults plus the inherited environment, with normal Codex configuration and shell settings authoritative.

Save runs nothing. Existing workers use updated lifecycle commands on the next explicit action/retry, while commands already executing finish with their original snapshot. Prior attempts and outcomes remain in history. Retained workers keep their prepared toolchain/environment. Failed setup is not silently rerun: ask the manager to Retry failed setup after correcting it, with its partial files preserved. Successful setup stays setup-once. Unresolved process ownership, missing worktree or changed permissions remain safety checks.

Cancel discards only the unsaved editor. Navigation between settings pages retains drafts. Invalid/stale saves leave saved settings and draft intact. Reload settings before retrying a stale save; copy any edits you need to retain first.
