# Concurrent worker lifecycle (AI-011)

The human talks only to one persistent manager. The manager submits explicitly agreed assignments with optional external issue linkage to independent Codex workers. Each task has its own Git worktree, Codex session, durable JSON record and readable Markdown projection. Local task identity, agent workflow, execution and external issue state are separate. The manager uses actual issue evidence for explicitly linked work; local tasks require no external ticket; setup does not create or mutate tickets.

`project.worker.maxConcurrent` controls executing capacity (1–8, default 2). Extra explicitly submitted tasks queue; no automatic backlog selection occurs. A worker that asks a question ends its turn and releases execution capacity. Answers are bound to that task/question/run and resume the same conversation/worktree. Reports and meaningful attention remain queued without forcing speech or opening the microphone.

Manager `worker_action` requests are durable and correlated by action ID, target task and expected run. Retry uses the same ID. Stop/pause ends only the target's owned execution and retains partial work, conversation and evidence. Resume/start creates a new attempt after reconciliation. Completed work remains available until deliberate disposal; dirty worktrees are not forcibly discarded. Controller restart adopts verified surviving execution instead of launching a duplicate. Each task reconciles independently so one failure cannot stall the rest. Closing voice/window does not stop the controller or detached workers. Quitting the instance stops its controller; retained workers and reports are recovered when the instance starts again.

## Agent-owned workflow and environments (GitHub #50)

Crew provides worker sessions, registered worktrees, reliable manager directions and durable history. Agents decide the work and initiate actions using tools, including commits, PRs, reviews and existing project environment commands. Native Codex resolves its own configuration, sandbox and approvals. Crew does not append separate business-action prohibitions.

`set_workflow_state` stores arbitrary project-defined visual state explicitly chosen by the manager or bound worker. Its value, actor, request/run/assignment identity and timestamp remain in history. Reusing the same request ID is idempotent. Process status, connectivity, pending native approvals and transport failures are separate evidence; ending a turn never sets workflow completion. Workflow state never gates messages or actions.

`get_project_environment` reads configured environment commands/instructions and retained evidence without executing commands. Dispatch and continuation do not automatically install tools, run setup/start/resume/readiness, or require environment readiness. Natural native connection closure observes captured service descendants without sending teardown signals; retained run references keep known live resources visible to archive and update checks. Agents remain responsible for project-specific services and external resources; process observation is not proof of complete external cleanup. The agent chooses and executes existing project commands through native tools and their approval policy. Saved legacy hooks and execution plans remain available as context. Previously supervised resources and cleanup evidence remain retained; explicit archive still checks ownership and refuses destructive removal of dirty or uncertain resources.

The manager overview shows compact labelled worker cards with task/ticket identity, useful progress, pending attention and verified execution timing. Selecting a card opens a read-only detail view across the main content area, with Conversation, Work notes and Links tabs. Return to the manager to direct work or review an item. Local worker status remains separate from external issue state. Execution elapsed time uses the recorded execution interval rather than counting waiting time as active work.

## Worker detail evidence contract (GitHub #14)

`GET /api/workers/<taskId>` is a project-scoped, read-only view. It returns `conversation`, `notes`, `links` and a nullable `historyNotice`. Existing same-origin and loopback checks apply. Rendering detail does not dispatch a worker, answer a question, acknowledge attention or mutate an external ticket.

New tasks retain an attributed `history` in their authoritative task JSON: the manager's submitted brief, actual worker reports, exact manager-relayed answers, lifecycle requests, and controller status transitions. These are observable task exchanges, not a copy of the manager's entire chat or private model reasoning. Question answers remain visible after a later run replaces current question/answer state. Run evidence is admitted only when its config matches the selected task/run/project. New runner `events.jsonl` records visible completed agent messages and command activity with task/run/time correlation; reasoning events carry no reasoning text. Older retained reports, final replies and command records remain readable. Missing historical exchanges are explicitly disclosed, never reconstructed as invented dialogue. Detail refreshes read the same durable records while the worker runs.

Shared prose lives at `tasks/<taskId>.notes.md` inside private project state. This is a real Markdown document, separate from the generated `tasks/<taskId>.md` orchestration projection. The manager's `update_work_notes(taskId, updateId, markdown)` and bound worker's `update_work_notes(updateId, markdown)` replace that document atomically with factual findings/decisions, subject to bounded text/secret checks. Worker writes require its current running task/run; manager writes enforce project scope. A repeated current update ID must preserve the same content. Until the first write, the UI states that no shared document exists. Notes changes are recorded in task history and therefore refresh through orchestration updates. The UI exposes no note editing or worker conversation input.

Links come only from URLs actually supplied in the ticket/resource fields or report evidence. Crew never derives a Linear URL from a ticket key or a GitHub PR from a branch. Only HTTP(S) URLs without embedded credentials are clickable; local worktree/repository/run/record paths are displayed as text. Private files remain outside the repository. Evidence reads are bounded and unsafe/unavailable files produce an explicit availability notice; they do not erase retained history.

## Changing an existing worker's model (GitHub #22)

Ask the manager to use a particular model for the selected worker. The manager records the actual user decision with `set_worker_model`, including an exact provider model ID and the current run ID read from `get_status`. This is pending intent for the next explicit continuation. It does not change the running turn, create a new task or start work automatically. If the change resolves an earlier model requirement in the assignment, the manager relays that decision separately; the agreed brief and original worker instructions remain preserved.

For a running worker that should transition now, the manager requests `worker_action` with `action: "pause"` and `cooperative: true`, waits for confirmed owned exit, then explicitly resumes. Cooperative pause never force-kills or automatically answers native approvals. A project runtime still requires its declared stop boundary. A blocked/paused worker can use its ordinary explicit resume after outstanding questions are answered and execution ownership is verified.

The next native worker checks the exact model ID through paginated `model/list` before resuming the retained thread. The model must be returned in the native thread response and supplied explicitly to the next turn. Catalog availability alone does not guarantee account access or successful generation; native errors remain errors. Missing or mismatched model evidence refuses a fallback turn. Recover by discussing a supported model with the manager and submitting a new authorized request, or retry the explicit continuation after provider recovery. Existing worktree, task records and conversation stay retained.

`get_status` and the worker detail show the requested model, pending/validating/selected/failed state and correlated native selection evidence. “Selected” means the native thread response confirmed that exact model and the turn start was acknowledged, not that the task succeeded. History retains the user decision and each selected/failed run. Exact request retries are safe and do not change future-task defaults, subscription authentication or native permissions.

A native provider can independently reroute a turn under its own policies. Crew preserves those policies and shows a separate “Rerouted by native provider” state with the reported destination model; it never continues claiming that the requested model was selected. This event is retained in correlated history for review with the manager.

## Repeated directions to retained workers (GitHub #50)

`assign_worker_followup` requires only the worker task ID, stable request ID and direction. The optional ticket defaults to the prior label. Observed run/assignment IDs and legacy review fields are provenance, never admission checks. Exact retries preserve the same direction. An active worker receives it through `turn/steer` in the same run, thread and worktree, without waiting for the assignment to finish. Startup waits only for the native turn acknowledgement. Idle workers continue the retained conversation normally; direction delivery never answers a native approval.

An idle direction resumes the same native Codex conversation and working directory with a fresh correlated run; live steering preserves the existing run. Dirty files, committed HEAD changes, missing old fingerprints, completed/paused/failed/questioning execution and changed configuration do not require review or adoption. An idle direction can supersede a prior question; live steering preserves current question/run correlation, and the answer tool still requires an exact match. Missing actual context or archived history-only records produce availability errors rather than replacement workers.

Assignments retain prior briefs, results, reports, notes and execution evidence. Live directions are actual user input; they do not rewrite the active system prompt or its saved snapshot. Both explicit live steering and new idle continuation read the current saved project worker instructions at their next Crew-owned delivery boundary, while prior run snapshots remain factual history. Saving Settings alone supplies no new input. Directions include their actual optional issue-link metadata, including explicit local/null intent. A saved-profile read failure sends no stale direction and retains recovery evidence without automatic replay. Controller restart reconciles live native processes and pending directions without duplicate turns. Native completed turns record execution results even without a report tool call; this does not verify semantic correctness or set project workflow state. Dirty worktrees still block destructive disposal.

Delivery records distinguish `pending`, `attempted`, `acknowledged`, `uncertain`, `rejected` and `failed`, with append-only attempt history and captured run/thread/turn identities. Rapid directions are attempted in stored order. Acknowledged steering is shown as native input accepted, never as completed work. Worker conversation and reports provide separate evidence that content was consumed. Steering leaves the current assignment, pending question and native approvals intact.

A definite no-active-turn rejection retains the message for ordinary idle continuation after confirmed connection closure. Unknown acknowledgement, mismatched turn acknowledgement or transport loss is never blindly replayed; retained pending delivery explains the uncertainty and requires investigation before continuation. A definite unsupported/rejected steering request is retained as failed. Preparation/update holds, archive/disposal and explicit lifecycle requests retain their existing boundaries. A slow steering RPC does not block approval or lifecycle observation. Already-running older supervisors cannot acquire new source behavior; this change applies when the updated runner is launched.

The opt-in `node scripts/worker-steering-subscription-acceptance.mjs` uses the normal signed-in subscription in its own disposable repository/controller, without voice or the installed app. It checks native acceptance and separate model reports before original-turn completion, then natural exit. Run only within authorized subscription acceptance scope. Synthetic regressions cover crash/ambiguous acknowledgement and protocol rejection without consuming subscription time.

## Archive a worker

When you are finished with a retained worker, open its Overview and choose Archive, then Archive safely. Your manager requests the existing safe teardown operation for that exact worker/run. Dirty files, unresolved work, unknown ownership and undeclared cleanup retain their existing protections. Pending or failed teardown remains in the workspace with its status/error so you can discuss recovery with the manager.

After teardown succeeds, the worker disappears from ordinary cards, counts and attention. Open Settings → Project settings → Archived workers for a simple table with one row per worker, newest known archive time first. Legacy records without a recorded time say Time unavailable. Each row offers Restore and Delete permanently; no archive detail view is included.

Delete permanently asks for confirmation before removing that worker's saved local Crew history, result, notes and per-run evidence. It does not delete unrelated tasks, existing worktrees/services, credentials or global Codex conversation history. Cancellation leaves the record intact; stale confirmations cannot act on a changed worker.

Restore returns the same worker's saved history to the ordinary workspace, labelled History restored with environment-needed guidance. It does not recreate its worktree or environment, run setup, queue an assignment, or start a worker/model turn. Discuss any later resource recreation with the manager: reconstruction is a separate explicitly directed operation, not a capability implemented by Restore. Saved briefs, results, run evidence and native conversation identity remain intact. Old questions and approvals remain historical rather than becoming active requests again. You can explicitly archive restored history again; record-only rearchive does not claim cleanup ran a second time, and refuses live/uncertain or reappeared resources.

Assignment completion, stop and pause do not archive a worker. Retained workers stay in the workspace until explicitly archived. Finishing an archive while its detail is open returns you to the manager without reconnecting the established call or discarding your draft.

The persisted lifecycle remains compatible with `dispose`; manager tools also accept `archive` through the same controller. `archivedAt` is recorded only after confirmed success. The shared worker-archive projection excludes finalized records from ordinary surfaces while leaving raw controller tasks available for historical lookup. An inconsistent record with a pending action or observed live execution remains visible for recovery. Generic updatedAt timestamps are never treated as archive evidence.
